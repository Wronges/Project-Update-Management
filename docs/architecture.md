# 系统架构

## 目标

第一阶段解决单台 Docker 主机的项目更新管理问题：

1. 统一展示项目、容器、当前镜像和更新状态。
2. 检查远端镜像后判断运行容器是否落后。
3. 从网页触发单项目或批量更新。
4. 保存更新前后镜像、执行日志、耗时和结果。
5. 不向浏览器开放任意命令执行能力。

## 组件

### Web Console

React 管理界面，只通过 HTTP API 读取状态和创建更新任务。前端不保存服务器凭据，也不拼装 Shell 命令。

### Control API

Fastify 服务，负责项目查询、更新检查、任务创建、状态聚合和日志读取。

### Project Inventory

`config/projects.json` 是受信任项目清单，记录：

- 项目名称和仓库地址
- Compose 工作目录和服务名
- 容器名及健康检查 URL
- 是否允许自动更新
- 更新策略：标准镜像更新或人工合并更新

项目清单由管理员维护，不允许通过普通更新接口修改。

### Docker Adapter

使用 `execFile` 调用 Docker CLI，命令和参数由服务端代码生成。所有工作目录必须来自项目清单，禁止客户端传入路径或命令。

检查流程：

1. 读取运行容器镜像 ID。
2. 执行 `docker compose pull <service>`。
3. 读取本地标签对应的最新镜像 ID。
4. 比较两个 ID，生成 `latest` 或 `update_available` 状态。

更新流程：

1. 对项目加互斥锁。
2. 拉取镜像。
3. 执行 `docker compose up -d --force-recreate <service>`。
4. 等待容器启动并执行健康检查。
5. 写入 SQLite 更新记录与完整日志。

### SQLite

保存任务与事件。配置仍由版本化项目清单管理，避免数据库和 Git 配置形成双重事实来源。

## 安全边界

- API 不提供任意 Shell、路径或 Docker 参数。
- 每个项目同一时间最多运行一个检查或更新任务。
- 批量更新只展开成多个受控单项目任务。
- 默认监听 `127.0.0.1`，公网访问应放在已有反向代理和认证之后。
- 所有写操作必须携带 `PUM_ADMIN_TOKEN`。
- 本地源码构建或带补丁项目使用 `manual` 策略，通用执行器不得更新。
- 后续增加用户系统时，更新接口必须要求管理员权限并记录操作者。

## 多服务器演进

第一版采用 `local` 执行器。后续增加轻量 Agent：

- Control Plane 保存服务器和项目元数据。
- Agent 在 Docker 主机本机执行受控操作。
- Agent 通过双向认证的长连接领取任务并回传事件。
- Control Plane 不保存服务器 SSH 私钥。

这种结构可以从当前单服务器平滑扩展，不需要重写 Web Console 和任务模型。
